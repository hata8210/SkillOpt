1参照文章：把「写 SQL + 自修正」做完形闭环训进权重（GRPO 时代形态）Agent Lightning + verl + LangGraph，2025-08

文章没有发明「写→执行→查→改」的循环（这套循环在 GRPO 之前就是用数产品里外挂自修正方法的骨架），它的贡献是用 GRPO 强化学习把闭环本身训练进模型权重：不微调一次生成，而是整条「自修正轨迹」参与优化。这套方法与 SkillOpt 属于同一家族 —— 差在能力被放在「模型参数」还是「外部技能/提示词」里。

1.1 Agent 状态机：与 SkillOpt 同源的闭环骨架

write_query按问题+表结构生成初始 SQL
→
execute_query在目标库真实执行
→
check_query检查执行结果/报错，判定对错
↻ 有错
rewrite_query带上一步反馈改写 SQL
→
END正确或 max_turns 上限

对应到 SkillOpt 抽象：write/rewrite = rollout（生成+执行）、check = 评估信号（可执行性 + 结果正确性）、执行错误 = 失败轨迹（reflect 的输入）、改写修复 = edit、多轮收敛 = gate 验收。差别只在于：SkillOpt 的「edit」批量写入技能文档，文章的「edit」直接更新模型权重（只训 write/rewrite 步，check 共享权重不单独训）。

1.2 训练架构：client-server 分布式 RL，奖励来自「执行结果」

组件作用
Training Server（agentlightning.verl）GRPO 训练循环（adv_estimator=grpo），托管 OpenAI 兼容端点的实时权重

奖励信号outcome-based：以「最终能否执行 / 结果是否正确」为唯一奖励 —— 与旧方法里「执行反馈即缺陷信号」同一哲学

1.3 文章关键数据：自修正收益被训练后「压进」单轮精度

图 1（数据来自文章评估）：同一模型 1 轮 vs 3 轮的生成精度。@2048ctx：73.2%→76.4%（+3.2pt，自修正还有肉）；@4096ctx：80.2%→80.4%（+0.2pt，几乎无增益）—— 上下文一足，多轮自修正基本被「一轮写对」取代。

图 2（数据来自文章）：把 check 也纳入训练：76.4%→77.6%（+1.2pt），但训练时间近乎翻倍 —— 显然不如把力气花在 write/rewrite 上。同时训练后轨迹收敛变快：transitions 1.65→1.44、3.30→2.60，即「模型学会了更少次改写就写对」。

  • 「RL training consistently boosts accuracy」是第一结论：每个模型从 initial 到 final 都有提升 —— 但这提升是权重内化获得的，与旧方法「把修复规则写进提示词」殊途同归，落点不同
  • 「Longer context helps」：2048→4096 把 1 轮精度从 73.2% 拉到 80.2% —— 长上下文本身补掉了不少「需要自修正才能补」的知识
  • 「More turns can help, but not always」：3 轮的上限收益随模型变强而消失 —— 这正是「GRPO 流行后一般不需要额外自修正」的数字证据

2旧方法（GRPO 之前）：SkillOpt 式「外挂」自发现自修正，早期用数产品每天都在用它适配模型与数据库本篇报告核心

在 GRPO 流行之前，「把语法能力训进权重」这条路走不通（微调成本高、数据少、模型迭代快）。用数产品实际做的是不动权重、只动技能/提示词层：每次 SQL 缺陷被真实执行暴露出来，就把它总结成一条修复规则沉淀进技能文档，下次生成直接带上 —— 这正是 SkillOpt 的训练循环，只是当年没有这个框架名，是产品里手工/半自动在跑。

2.1 为什么必须「迭代自发现」：组合爆炸 + 可执行性才是唯一真相

图 3（示意结构，非特定产品数据）：用数产品要覆盖「多个大模型 × 多种数据库方言」的矩阵。每个格子的错误模式都不一样：模型 A 的 SQL 习惯 ≠ 模型 B；MySQL 能跑 ≠ ClickHouse/Doris/Hive 能跑。旧方法的价值 = 在一个格子里积累的「缺陷清单」可以自动总结并注入下一个格子的生成，把 M×D 次人工排查变成「M×D 次自动迭代」。

典型 SQL 缺陷/语法兼容问题的类别（示意清单，用来理解「自发现对象」）

缺陷类别示例（不同方言表现）为何模型原生易犯
分页语法LIMIT/OFFSET（MySQL、PG）vs LIMIT n,m vs 无（某些 MPP）训练数据以主流方言为主
保留字/大小写order、group、rank、rows 等作列名需反引号/双引号，且方言引号规则不同NL→SQL 转换忽略方言词法
函数命名差异IFNULL vs COALESCE vs nvl；date_add 语义差；字符串函数族差异多方言函数表无法全记
类型/隐式转换字符串→数字、时间类型比较、NaN/Null 语义差异DDL 类型信息未被利用
NULL 语义=NULL vs IS NULL；COUNT(列) 与 COUNT(*) 不同伪 SQL 混淆
执行器限制子查询嵌套深度、CTE 支持、窗口函数实现差异模型不知道目标执行器能力边界
版本/配置差异同库不同版本：函数废弃、sql_mode、时区知识时滞

旧方法与 SkillOpt 六步的对应关系

旧方法动作SkillOpt 阶段
生成 SQL 并执行ROLLOUT（生成+真实执行）
报错/结果错误 → 反思原因REFLECT（失败轨迹→edit）
修复规则去重、合并AGGREGATE + SELECT（控量）
规则写入技能/提示词文档UPDATE（patch 技能）
用回归集验证「修复有效且无回退」EVALUATE（gate 验收）

差别：旧方法绝大多数时候跑在「无权重更新 + 人工兜底」的轻量模式；SkillOpt 把它自动化、框架化了 —— 这也解释了为什么 SkillOpt 的价值更多在「技能/提示词优化」而非「SQL 语法」。

2.2 新旧两种范式的代价差别：一次适配 vs 一轮又一轮

图 4（示意曲线）：旧方法在每个「模型×库」组合上的典型路径 —— 上线初期缺陷密集暴露（可执行性差），靠自发现+沉淀快速收敛；但每次换模型或换库都要重来一小段（知识是模型相关/方言相关的）。GRPO 之后，主流组合这条曲线几乎变成「开箱即用」，只剩长尾组合需要外挂。

旧方法的成本真相（为什么它当时必须存在、又为何被取代）

  • 必须存在：当时模型（尤其 API 模型/本地小模型）的方言知识不可靠，真实执行能立刻暴露缺陷 —— 「可执行性 = 最便宜的自动验收信号」，这比人工 review 便宜一个量级
  • 持续投入：每适配一个模型/一个库，都要跑一遍「缺陷发现→规则沉淀→回归验证」，规则库跟着模型和库版本走，维护成本线性增长
  • 知识是外挂的、可解释的：这是它最大的优点 —— 每条规则都能查、能改、能审计
📌

旧方法定位总结：它不是「训练模型」，而是「给生成器配一个会自学习的纠错器」。GRPO 之前，这是把「可执行 SQL 知识」注入产品的唯一低成本杠杆；但它把知识放在模型外面，天然有维护负担 —— 这正是 GRPO 时代它被边缘化的结构性原因。

3分水岭：GRPO 强化学习流行后，为什么「一般不需要」再额外用类似方法优化 agent能力从技能层搬进权重层

GRPO（以及 RLVR 一族）把「写对 / 改对」的偏好直接优化进权重 —— 文章就是范本：把 write/rewrite 整条自修正轨迹用执行结果做 reward 训进 Qwen2.5-Coder-3B。效果是：单轮就能写对，自修正从「必需品」降级为「保险丝」。

3.1 文章数字支持「不再需要」的三个论据

图 5（文章数据）：同模型不同上下文的 1 轮 vs 3 轮精度。长上下文 + 训练后，1 轮已接近 3 轮上限 —— 自修正轮次的价值被权重内化吸收。

  • 论据一 · 一轮就够：@4096ctx 1 轮 80.2% vs 3 轮 80.4%，差 0.2pt —— 产品里完全可以接受「开一轮直出」，省掉 agent 循环的延迟与 token
  • 论据二 · 自修正收敛：训练后 transitions 从 1.65/3.30 降到 1.44/2.60 —— 模型「更少改写就写对」，说明修正能力已被内化为生成习惯
  • 论据三 · 外挂收益递减且昂贵：把 check 也训进权重只换来 +1.2pt（76.4→77.6），训练时间却翻倍 —— 边际上「技能层再修补」已经拼不过「权重层砸预算」

3.2 外挂修正层 vs 权重内化：一张图看清「时代切换」

维度旧方法（SkillOpt 式外挂）· GRPO 之前文章做法（GRPO 权重内化）· GRPO 之后
能力载体技能/提示词文档里的修复规则、few-shot 示例模型参数（write/rewrite 策略）
边际适配成本每「模型×库」组合一轮自发现+回归，规则库随模型/库版本维护一次 GRPO 训练（GPU、数据、2 epochs），之后开箱即用
可解释性高：每条规则可查可改可审计低：知识藏在权重里
稳定性/泛化易过拟合当前模型与方言；换模型规则可能失效跨问题分布更稳，长上下文 + 训练后 1 轮即达上限
运行成本每轮生成都带大提示词（规则+示例），还要跑 agent 循环单轮直出，无 agent 循环
训练门槛低：无需 GPU 集群，轻量迭代高：需要 verl/vLLM/GPU 与数据管线
⚖️

结论：GRPO 之后，「能不能写对 SQL」这件事的默认答案变成了「看权重」；外挂技能优化退到四个角落里：① 不能/不愿微调的 API 模型；② 私有库、内部库、长尾方言（无公开训练数据）；③ 小型/私有模型没有 GPU 预算；④ 技能优化的对象本来就不是语法，而是产品规则/评分细则/输出格式这类「可解释的业务知识」 —— 后者的代表正是本仓库的 interviewer 实验。

4仓库证据链：SkillOpt 家族方法今天在做什么，以及它与这篇文章的关系outputs/searchqa_quickstart + interviewer 两篇报告

本仓库的 searchqa / interviewer 实验，就是「旧方法」框架化之后的当代形态：同样的 agent 闭环、同样没有权重更新、同样的「失败轨迹→edit→gate 验收」。它们的表现恰好印证了分水岭论断 —— 在通用/可训练领域，外挂优化收益有限；在「业务技能」领域，它仍是不可替代的杠杆。

图 6（本仓库 outputs/searchqa_quickstart 真实数据）：SkillOpt 在 searchqa（文本问答）环境 400 样本、10 步训练：selection 0.480→0.515（+3.5pt）、test 0.494→0.537（+4.3pt），但 10 步里 9 步 REJECT、仅 1 步 ACCEPT —— 收益存在，但相对 GRPO 权重训练的幅度（文章 73→80）明显更小、更慢。

图 7（前两篇 interviewer 报告数据汇总）：同样一套方法，在「业务技能」任务上收益显著：27 分钟学出与人工模板 8/8 一致的评分细则（selection 0.274→0.332）；3 条超少样本从 0 分到 best 0.667 / test 0.667→0.767 —— 这类「规则、守则、输出格式」正是权重内化力所不及、而技能优化最擅长的地方。

早期（GRPO 之前）· 用数产品每个「模型 × 库」组合一轮 SkillOpt 式外挂自发现/自修正：SQL 缺陷→规则沉淀→回归验证，语法兼容知识住在提示词层
GRPO/RLVR 兴起（2024H2 起）verl 等框架把 GRPO 变成标配；可执行性/结果正确性直接当 reward，语法能力开始进权重

最终结论一条线：SQL 语法兼容能力从「外挂技能」搬进「模型权重」，是 GRPO 时代最划算的一笔迁移——它把用数产品从「每个模型每个库都要养一套纠错规则」里解放出来。SkillOpt 式方法没有消失，它退到了真正不可替代的位置：处理那些 GRPO 训不进去的、可解释的、会随业务变化的「技能知识」（评分细则、输出守则、产品规则、评估口径）。读懂这篇旧法回顾，就懂了 SkillOpt 今天该被用在哪儿。
