1问题一：样本不够 + 偏主观评判 → bias 大 → 得分飘忽，易错过好 edit、易陷局部最优interviewer_blank & blank2

interviewer 环境的「分数」由三层主观/离散的东西构成：① 人工标注的 ground truth（通过 / 不通過，本身就是二值主观判断）；② 目标模型单次采样的总分 <score>；③ evaluator 把总分压成 0 / 0.3 / 1 三档奖励。三者在 3 条样本上取平均，得到的信号分辨率极低、噪声极大。

1.1 评分信号本身就很粗糙（evaluator 机制）

环节机制问题
人工标签通过 / 不通過（二值）主观，无分数维度
模型输出<score>X.X</score>（0~8）单次采样，LLM 随机
zone 判定≥6.5 录用 / ≤4.0 拒绝 / 其余中间区悬崖：6.4→6.5 奖励 0.3→1.0
奖励命中=1.0，中间区=0.3，错/解析失败=0每样本只有三档

关键细节（skillopt/envs/interviewer/evaluator.py）：只要模型输出格式可解析且落入中间区（4.0 < 分数 < 6.5），就无条件送 0.3 分；而解析失败直接 0 分。这意味着「格式对但评分烂」和「评分好但格式错」都会被同一个粗粒度信号惩罚，技能优化很难从中分辨自己该改什么。

悬崖示例：候选人真实应「拒绝」（≤4.0），模型给 6.4 分 → 0.3；给 6.5 分 → 0.0。0.1 分的差距决定 0.3 的奖励落差，而 0.1 分在单次 LLM 采样下完全是噪声。

1.2 得分飘忽的直接证据：同一个技能，多次评测分数差可达 0.19 ~ 0.67

图 1：同一技能在不同评测时刻的得分观测（真实数据）。S0＝初始空白技能在 3 条样本上的三次评测（baseline selection / step1 rollout / baseline test，同一批样本 full split），实测 0.0 / 0.333 / 0.667 —— 技能完全没变，分数从 0 到 0.667。S1＝blank1 第一步接受的技能在 34 条样本上的三次观测（selection 0.332、rollout 0.374、rollout 0.188）。current＝blank2 第 4~10 轮训练中近似同一技能的 7 次 rollout 观测（0.333~0.767）。

1.4 reward 分辨率：3 条样本只有 10 个可能的分数

图 3：n=3 时 selection 分数只能是 0.1 间距的离散值（0.0, 0.1, 0.2, 0.333, 0.433, …）。0.4333 平台附近的最小分辨率是 0.033~0.1 —— 一次「把 1 条样本从中间区 0.3 提到命中 1.0」的改进（+0.233）可以测到，但「让 0.3 中间区接近命中」或「让 1.0 保持 1.0」这类边际改进完全测不出来。

  • 对比：n=34 时分数步长 ≈0.009，能分辨的改进粒度约为 3 样本的 10 倍
  • 3 样本下 selection 值域被钉在 {0, 0.1, 0.2, 0.333, 0.433, 0.533, 0.667, 0.767, 0.867, 1.0}，这也是为什么两个实验里反复出现 0.4333 / 0.6667 这些「幸运数字」

更进一步的证据：被拒候选的 selection 分布（0.1 / 0.4333）与「当前技能」自身在 slow update 观测里的分布（0.1 ~ 0.767）几乎重合 —— 说明 accept/reject 的输入信号不足以区分「候选更好」和「采样运气差」。没有任何代码把被拒候选的部分 edit 保留下来重试，好 edit 一旦被拒就永久丢失。

1.6 后果 B：容易陷入局部最优（假平台期）

图 4：blank2 中 best 得分从 E2 起卡在 0.4333，连续 8 个 epoch 无 step 级提升；而同期的 rollout 观测（虚线）在 E9/E10 已到 0.7667 —— 训练信号已经暗示技能变强，但 selection 评测（单次采样、同 3 条）始终报 0.4333，制造了一个评测噪声造成的假平台期。最终突破（0.667）来自训练结束后的最终评估，而不是任何一步的梯度更新。

  • 34 样本的 blank1 同样存在：best 在 step1 后连续 2 个 epoch 无任何提升（2 次 skip），rollout 在 0.19~0.37 之间抖动
  • 「严格大于当前才 accept」的 gate 在小样本噪声下等价于「拒绝所有与当前持平或偶发低分的候选」—— 保守，但代价是平台期和错过真改进
⚠️

问题一结论：interviewer 场景的分数 = 主观标签 × 单次采样 × 三档奖励 × 3~34 条样本，噪声足以吞没 0.1~0.3 的真实改进。当前管线既不重复采样（每次评测只跑 1 次），也不重试被拒候选，因此在「样本少 + 偏主观」的场景里，得分飘忽、错过好 edit、假局部最优是结构性的，不是调参能完全解决的。

2问题二：开启 slow update 后，等于给模型开了一个「可作弊的缺口」，epoch-wise edit 必须小心接纳interviewer_blank2 · 代码级证据

slow update 的定位是「跨 epoch 纵向分析后，把规律性守则写进技能的保护区」。设计初衷合理，但在当前实现下它走了一条不评测、不过 gate、直接改写的捷径 —— 与 step 级 edit 的严格验收流程形成鲜明对比。

2.1 机制缺口：force-accept（unconditional），注入不经过任何验证

# 训练日志（logs_detail.txt 开头） [slow update] acceptance=force-accept (unconditional) # trainer.py 中 force-accept 分支（默认路径） current_skill = replace_slow_update_field( current_skill, slow_content) # 直接改写，无评测、无 gate sel_cache[slow_candidate_hash] = (current_score, 0.0) # ↑ 把【旧技能的分数】登记到【新技能】的缓存槽里
  • 默认配置：slow_update_gate_with_selection=false，注入完全不评测；代码里 gated 模式（评测 + gate）虽然存在，但本次实验没启用
  • 只写 current，不写 best：守则被塞进当前技能继续训练，best 仍是 step 级最优（0.4333）—— 直到训练结束才被一次「最终评估」翻盘（见 2.2）
  • 保护区 READ-ONLY：slow_update.py 把 SLOW_UPDATE 区设为 step 级 analyst 的只读区 —— 一旦注入了一条坏守则，正常的 per-step edit 无法修正它，只能等下一轮 slow update 覆盖
  • 缓存污染：sel_cache[新hash] = (current_score, 0.0) 把从未在注入后技能上测量过的分数登记为新技能的成绩 —— 后续若命中同 hash，会读到一份「伪造」的评测分

2.2 最危险的一环：最终晋升 = 单次采样「一锤定音」

# 训练日志（logs_detail.txt 结尾） [final skill val] items=3 final_selection_hard=0.6667 gate=0.6667 (best=0.4333) [promote] final 0.6667 > best 0.4333 → final becomes new best (step 10, origin slow_update_epoch_10)

trainer.py 2179-2230 行：最终技能与 best 不同时，只跑一次3 条样本的 selection rollout，若 > best 就无条件 promote。

  • 0.233 的提升正好落在噪声带里：n=3 同技能两次评测差的中位数就是 0.233（见问题一图 2），而 final（0.6667）vs best（0.4333）的差恰好是 0.233 —— 这次「突破」与「同技能测量噪声」在统计上不可区分
  • 同一技能被测出过 0.1：E9 的 slow update 把当前技能测到 0.1000，E10 又测到 0.7667；最终评估再测一次就取了 0.6667 —— 三次测量、三个分数，恰好是「挑到一次好采样」
  • step 级 gate 用「严格大于」保护了 8 个 epoch 的 0.4333，最后却被一次不加 gate、不重复采样的最终评估绕过

2.3 内容特征：第一类守则是「打评测器的补丁」，而不是评分本身

看最终 best_skill 里 SLOW_UPDATE 区的 15 条守则，能明显发现「作弊缺口」的痕迹 —— 模型学会了怎么让评测器给分，而不是怎么评得更准：

守则类别代表内容为什么算「缺口」
① 输出铁律（规则 1-4）必须输出一行 <score>，禁止前后缀文字，宁可 0.0 也不空白直接利用 evaluator「解析失败=0」的漏洞 —— 基线 0 分的根因是格式，慢更新第一课学的不是评分而是「让解析器拿到分」；中间区还能白拿 0.3
② 证据锚点（规则 5-13）保洁=0.5、保安/物管=1、「识少少」=0.5 …这部分是真实的评分知识，属于合理收获 —— 但它和①混在一起，无法与「评测器 hack」分开审计
③ 防漂移 + ④ 自检同一证据同一分；发送前一秒自检格式自检规则再次聚焦「格式」而非评分；防漂移是好守则，但它本质是在修 slow update 自己反复注入造成的不一致
特殊规则 13面试官介绍岗位是「洗手间清洁/收潲水」时不要质疑与保安员不一致这是从 3 条保洁样本里观察到的一次性现象 —— 在更大样本分布上会变成错误先验；过度拟合样本噪声被写进技能且无法被 step edit 修改

2.4 注入的即时收益无法验证：7 次注入后 selection 纹丝不动

图 5：每轮 slow update 注入的守则字符数 vs 注入后下一轮的 current selection 得分。7 次注入（831~1475 字符）之后，selection 全部仍是 0.4333 —— 没有任何一次注入在正常评测里被证明「有效」；唯一一次「见效」就是 2.2 里单次采样的最终评估。同时守则长度忽大忽小（S8 时技能总长反而从 2856 缩到 2752），说明内容是模型自由发挥，长度与质量都不可控。

🔓

问题二结论：slow update 的「保护区 + force-accept + 最终单次晋升」组合，等于给了优化器一条绕过全部验证的路径 —— 它可以在不评测的情况下改写技能，在无法证明有效的情况下最终晋升。epoch-wise edit 必须像 step edit 一样走「评测 → gate → 可回滚」，否则它就是训练管线里的后门。

改进方向（代码已支持一半）：设置 slow_update_gate_with_selection=true；注入候选用多次采样投票的 selection 分参与同一 gate；禁止守则区写「输出格式/评测器相关」指令（或单独隔离审计）；限制守则区长度与「只能写可验证的事实性规则」；最终晋升也需要重复采样 + 显著超出噪声带（如 > 当前 best + 2×σ）才允许 promote。

3问题三：闭环训练管线仍有不小的成本 —— 看 interviewer 的定制数据结构与代码数据 + 代码盘点

「闭环」= 原始数据 → 物化/split → 环境适配 → 训练（rollout/反思/评测）→ 记忆（slow update / meta skill）→ 产物。这个闭环里真正「贵」的不是优化器本身，而是数据准备、人工标注、环境定制、评测与记忆环节。

图 6：两次训练的总耗时分解（基于 history.json 的 per-step timing 与 logs_detail.txt 的 slow/meta 耗时）。blank2 中 slow update + meta skill 合计 ≈1562s（52%）；3 条样本跑 10 个 epoch，每轮都要付一笔固定的「纵向对比 + 记忆」开销，因此样本越少，单样本训练成本反而越高。

  • 单步成本结构：blank2 每步 rollout 仅 12~48s（3 条），但 reflect 66~83s、evaluate 41~44s —— 反思与评测是每步的固定大头；blank1（34 条）单步 rollout 196~267s、evaluate 235s，样本量直接把 rollout/eval 拖慢
  • 评测重复消耗：同一个 selection 集被反复 rollout（基线、每步候选、slow gate、最终评估、test），没有任何评测缓存复用（除 sel_cache 但只按 hash 命中且被 2.1 的污染削弱）
  • 极端反直觉：3 条样本的 blank2 用 token 1.64M、耗时 3018s，反而超过 34 条样本的 blank1（1.71M token、1611s）的一半 token、近 2 倍时间 —— 钱和时间主要花在 10 个 epoch 的反思 + 记忆循环上

问题三结论：闭环管线真实成本 = 数据标注 + 环境定制（≈750 行）+ 评测迭代（repeat rollout）+ 记忆环节（slow/meta，blank2 占时间 52%、token 31%）。「优化本身」很便宜，但把它包成一个能跑、能测、能记住的闭环很贵；对 3 条样本的微任务，固定成本完全压过数据本身的价值。降本方向：评测结果缓存复用、慢更新/记忆降频（如每 2-3 epoch 一次）、轨迹截断恢复、共享岗位无关的评测器抽象、多采样投票只对「有争议」的决策开。

4总结：三个问题是一件事的三个侧面 —「信号」不可信，于是「门」不敢开、账也算不清建议按优先级落地

① 得分飘忽 / 错过 edit / 局部最优同一技能实测 0.0/0.333/0.667；n=3 同技能两次评测差>0.1 概率 76%；best 卡 0.4333 达 8 个 epoch评测重采样 3-5 次取均值 + 被拒候选的 edit 进入「候补池」重试 + 有争议分数（差 < 2σ）标记为 tie 不据此做决策

③ 闭环成本高3 样本训练 50 分钟 > 34 样本 27 分钟；slow+meta 占时间 52% / token 31%；定制代码≈750 行评测缓存复用 + slow/meta 降频 + 恢复轨迹截断 + 抽样投票降本（只对争议候选开）
一句话总结：interviewer 这类「样本少、评分主观」的任务，当前 SkillOpt 管线的瓶颈不在优化算法本身，而在评测信号太贵又太脏 —— 信号脏（0/0.3/1 三档 × 单次采样 × 3 条样本）导致 step 决策被噪声主导、假平台期和误拒好 edit；唯一绕过脏信号的门（slow update force-accept）反而成了未经验证的后门；而支撑这个闭环的评测与记忆开销又把小样本训练的边际成本推得过高。把「评测变准、变便宜、变可复用」放在「让模型更聪明」之前，是这个场景最值得先做的事。
